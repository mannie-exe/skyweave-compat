# Distant Horizons integration

Skyweave: Compatibility Patches uses DH's ordinary terrain generation, storage and rendering. It does not provide a separate terrain predictor. Optional hooks target DH 3.3.3 on Minecraft 1.21.1. The compile-only artifact is pinned by SHA-256 in `build.gradle`; `FeatureSelection` and active feature tests must agree. [Dependency admission](dependencies.md) owns development-versus-installed diagnostics and explains why these private contracts do not accept an arbitrary DH patch. Historical scene evidence below retains its actual NeoForge version.

## Lifecycle ownership

DH's `ClientLevelWrapper_neoforge.getWrapper` publishes a server-keyed wrapper after retiring its predecessor. Concurrent readers can claim the same predecessor, and delayed unconditional removal can erase a replacement. `ClientWrapperHandoffMixin` publishes the replacement under the cache lock before cleanup. `WrapperCache` removes entries only while the retiring wrapper owns them. Cleanup runs outside the cache lock, and delayed upstream publication cannot overwrite a newer owner. This hook loads only on physical clients.

`ChunkUnloadBudgetMixin` limits each shutdown unload pass to 1,024 queue polls in Sky Archipelago dimensions when DH is installed. An unfinished generation reference can requeue an unload callback. Draining indefinitely prevents queued server cleanup from releasing that reference. Yielding preserves queued work and lets Minecraft service the executor between passes. Running servers and foreign generators retain native behavior. Previous integrated-client investigation observed this livelock; verification of the extracted fix is tracked in [verification](verification.md).

## Cache identity

`WorldIdentity` persists one UUID per saved world. `WorldLevelKeyMixin` uses that UUID and a hash of the dimension ID in DH's normal server-key handshake. Creation is enabled by default through `distant_horizons.world_cache`; an explicit false setting selects no cache hooks, including for a save with an existing marker. Re-enabling reuses its marker. Server-side database paths do not change. See [operator configuration](../configuration.md#distant-horizons) before enabling it on an existing installation.

`LegacyCacheMixin` prevents DH's pre-2.3 dimension-only cache import only for the complete Skyweave: Compatibility Patches UUID key format. It leaves the old directory untouched. Ordinary and merely similar keys retain native migration. This avoids attributing an unidentified old save to a new UUID cache; it is not a general cache migration tool.

## Luminous columns and fluid colors

DH 3.3.3's `FullDataToRenderDataTransformer.setRenderColumnView` transfers an ignored noncolliding block's color and material to the segment below when `tintWithAvoidedBlocks=true`. With glow lichen, one thin surface block can therefore make a tall stone segment emissive. The same path can replace lava's or water's color and material. Complementary/Euphoria's `DH_BLOCK_ILLUMINATED` branch makes the resulting gray-green segment particularly bright.

The physical-client probe reproduced this through DH's actual conversion code: lichen above a 40-block segment changed stone, lava and water to material 15 and color `ff72847a`. Without lichen, lava was material 6 / `ffd96f21` and water material 12 / `bf2b529f`. A rendered stone/lichen fixture produced a white stripe at night. Native source and flowing lava states retained the correct orange particle color; this was not a general failure to recognize flowing lava.

The smallest verified remedy is to append `minecraft:glow_lichen` to `client.advanced.graphics.culling.ignoredRenderBlockCsv` in DH's configuration. Preserve the other entries. This excludes lichen from distant representations; native lichen, fluid rendering and ordinary foliage tinting remain unchanged. Reopening the same fixture and LOD database removed the stripe and preserved all three substrates' original materials and colors. No cache deletion or new fluid Mixin is needed. Skyweave: Compatibility Patches does not rewrite an operator's DH configuration; the modpack owns its chosen default.

## Client completion wait

The client completion adaptation is separate from the installed server unload-budget repair. DH3.3.3 `PriorityTaskPicker.shutdownNow` shuts down its executors, awaits each for up to five seconds, and then uses its native interruption fallback. The wait is already completion-aware. `SharedApi.setDhWorld` already closes the old world before shared pools; changing that order or shortening the timeout is not the proposed repair.

The retained causal experiment found render-loader workers joining upload futures while the owner render thread waited for those workers. Servicing `RenderThreadTaskHandler.INSTANCE.runRenderThreadTasks()` on that actual thread/context allowed native termination. Its early-disconnect databases were empty, so it establishes the dependency mechanism, not useful-data durability, full-pack cost, shader lifetime, or integrated shutdown acceptance.

The client-only wrapper targets the exact `PriorityTaskPicker.Executor.awaitTermination(long, TimeUnit)` invocation. It admits only the actual native render-task owner thread and still-current main GL context. It computes one deadline from the original amount, checks executor termination before servicing callbacks, and services only the existing native render-task queue between completion-aware slices. Context and ownership are checked again before each service. Interruption, the original total deadline, and native fallback remain authoritative; the adapter does not create tasks, cancel useful futures, or recycle checked-out buffers to force completion.

Use the supported native queue API, not a copied renderer or general Minecraft task pump. Verify which awaited pools actually depend on that queue. Native callbacks retain their source/buffer ownership and ordinary exceptional cleanup. If the context is absent, foreign, lost, or not on the owner thread, delegate the legitimate remaining wait and native fallback. No client class or GL probe may resolve on a dedicated server. A new lifecycle selector stays independent of queue tuning, cache identity, shaders, and the installed server unload feature.

Actual TCP diagnostics on engineering candidate 5 expose an earlier dependency. `DhClientWorld.close` completes its network session before joining individual level-close futures. At that join, 64 completed wire futures have 64 compression callbacks queued with none running, while four render-loader workers wait on upload futures. The later executor wait has not been reached. Admission guards alone do not repair this close: the native five-second network warning remains.

Candidate 6 also wraps the original level-close `CompletableFuture.join` with the same captured render owner. It services only the existing DH render queue while that original future is pending. Terminal futures are delegated without service; wrong or lost owners and interruption retain the native uninterruptible join and its result, exception, or cancellation. The original network timeout, future owners, and native level/pool order remain unchanged.

The current Zfastnoise-free production cohort passes a matched candidate-6 TCP control with only `client_completion` changed. With it disabled, both native network closes reach their original five-second warning, leaving 64 and four compression callbacks queued at the sampled close completion. With it enabled, both close futures settle with zero queued callbacks and no warning; the observer records 86 native render-queue service calls during world close. Both clients preserve the same decoded four-solid-cell column across reconnect and reload, retire the observed workers and buffers, and exit normally. The enabled client returns all 6,348 observed CPU loans and deletes all 763 observed uploaded VBO generations in their native context. This establishes the earlier dependency boundary on this profile, not a sustained performance, final-world collection, shader, or complete C4 acceptance claim.

Qualification needs real nonempty terrain/LOD data, queued uploads, integrated stop, TCP disconnect, same-process reconnect, resource reload, and supported shaders off/on. Preserve decoded useful data and source identities across a second-JVM reopen; database integrity/count alone is insufficient. Track actual workers, callbacks, checked-out/returned buffers, GL state/errors, old-world references, and normal process completion. Retain the exact deadline in every control. Three matched interleaved nonempty-data comparisons are required before a latency claim; record useful output and tail stalls as well as named await duration.

World/session/renderer retirement must invalidate publication without pretending native work stopped. Delayed wrapper removal remains owner-checked by the existing handoff adapter; late uploads cannot attach to a new section with reused coordinates or GL identifiers. Release only owned handles. Recheck `DhClientLevel`, client-side/render-source close, `LodRenderSection` upload futures, `LodBufferContainer` scheduling, `RenderThreadTaskHandler`, and executor await/interrupt semantics when dependencies change. Retire this wrapper only when the released native owner resolves the same dependency and passes useful-data/resource controls.

### Candidate implementation

`distant_horizons.client_completion` selects only `ClientCompletionWaitMixin` on the physical client for exact DH 3.3.3. `CompletionAwait` retains the native executor, total wait budget and interruption outcome, checks termination before servicing, and delegates the remaining wait when owner/context admission is lost. It uses `RenderThreadTaskHandler.isCurrentThread` plus the actual Minecraft render thread and main GLFW context; no copied task queue or private owner accessor is needed. Native callbacks retain their own exception and resource handling. An individual native callback may itself exceed its ordinary budget; the wrapper does not preempt useful GL work or promise a hard bound on arbitrary callback execution.

The real Mixin transformer checks the pinned shutdown invocation. Focused real-executor tests cover owner-dependent completion, terminal behavior without renderer access, context loss, remaining timeout and interruption. These checks do not establish nonempty DH durability or visual/resource behavior; those native combined controls above remain required before final qualification.

The retained predecessor native server output control reads real DH data from a naturally loaded vanilla flat-spawn column. Original and repaired queue paths both preserve its four solid cells, three material strata, and actual source height. Separate JVMs then open private copies of the closed original SQLite store through the native repository and DTO decoder; these copies are never registered as live providers, so chunk regeneration cannot replace their evidence. Decoded material remains identical. Native worlds retire, observer readback workers terminate, and every process exits normally. The store marker retains the donor world's seed separately from the fresh comparison world's seed.

The main-based cohort extends this control to the entire loaded flat spawn chunk: 256 columns, 98,304 occupancy cells and 1,024 solid cells. Original and repaired output and independent native closed-store decoding retain the same compressed image. DH's original `FullDataSourceV2.updateFromDataSource` invokes `FullDataOcclusionCuller` under `VISUALLY_EQUAL`; the native image differs from 450 physically buried material cells. Each difference is independently enclosed by six loaded opaque neighbors. Occupancy and exposed materials must remain exact, and the observer must not load a neighbor to justify a difference. Treating compressed LOD data as a physical block inventory would be an invalid oracle.

A separate production-loader client with Sodium 0.8.13 observes nonempty native upload futures during both disconnects, same-world reopening in the same JVM, new uploads after resource reload, unchanged decoded terrain, native world retirement and normal process exit. It observes the actual native render-task queue being serviced inside shutdown. This is a bounded repaired-path witness, not a numerical latency comparison or full-pack qualification. Earlier minimal clients without Sodium retain native Apple Metal/OpenGL failures on both original and repaired paths; the Sodium witness does not explain or repair them.

The opt-in GPU resource observer additionally verifies native deletion of uploaded VBO generations synchronously on their actual main context. Its first useful run records 1,379 verified deletions and 1,041 later GL-name reuses without confusing them with old live buffers. The first world's client-level and DH-world weak references clear naturally; final-world collection is not established before process exit. These are observations of selected uploaded buffers, not all native allocations, pool return or total GPU-memory measurements.

Client observers must use retained native level identity. In this pinned DH version, `DhClientServerLevel.getClientLevelWrapper()` returns the process-global current client wrapper even for another dimension. Compare the retained server-level object with the current integrated server's actual dimension owner; for remote clients, compare the actual client-level object. Wrapper presence alone does not establish the source or session.

These controls do not establish complete distant-field coverage, queue-overload/fairness behavior, TCP reconnect, supported shaders, checked-out buffer/GL retirement, old-world collection or sustained performance. Those acceptance controls remain selected.

Queue progress is specified separately below; native worker tuning remains with its actual configuration owner. Lower worker CPU, an early wrapper exit, or a clean title screen does not establish preserved generation, uploads, or storage.

## Update queue progress

`distant_horizons.update_queue` selects the exact DH 3.3.3 native chunk-update manager on either physical side. After a non-progressing pass with queued updates, only that manager's own worker waits, for at most 50 ms or the remaining native debounce interval. A successful dispatch keeps native progress immediate. External enqueue, center updates, clear, and close wake the worker; its own center update does not fabricate new work. Keep native queue/debounce identity, priorities, source ownership, and executor behavior. No caller sleep, new content cutoff, or copied task queue is introduced.

The new adaptations default off in this engineering cohort until the full affected native acceptance is qualified. Explicit false remains authoritative. They are independent of the installed unload, cache-identity, and client-wrapper handoff adaptations. Their current real-executor and transformed-native tests establish narrower boundaries than complete useful-data, client-upload, lifetime, or performance acceptance.

## Network request lifecycle

`distant_horizons.network_requests` is a separate, default-off physical-client adaptation for exact DH 3.3.3. Native TCP controls verify actual loopback connections across two connections per process and an independent second JVM using the first client's closed cache. Native data matches the delivered physical column, reopening/reload and the observed render resources retire, and the second process observes 119 successful native DH payload decodes. Those process-total wire observations do not attribute every sampled column exclusively to the wire.

The native logs also retain remote-generation request-queue shutdown timeouts. Passive observation records 7,156 submissions after closing has started, including new pending results. Native tick refuses to dispatch once `closingFuture` is present, while the original submit method still adds requests. The first diagnostic's bounded late-request records obscured later close events; the next observer prioritizes close events and reports omitted late details separately. These are qualified admission findings, not a proved explanation of every timeout or a complete network-retirement claim.

The engineering adapter serializes submission and close publication with the native tick monitor. Before closing it delegates the original request unchanged. After closing it returns a new, already-cancelled result for that refused submission, without cancelling existing shared data futures or creating a placeholder terrain result. Repeated close requests reuse the native queue's existing close future, including its failure or cancellation. The original close body, cancellation policy, semaphore accounting, and five-second diagnostic remain unchanged.

Matched candidate-5 TCP controls show that the guard prevents entry into the original submission body after close begins, while preserving useful data and reconnect. That passive body counter does not count refused attempts outside the body. The guard alone leaves the five-second close warning. A later trace finds already-completed wire futures whose callbacks remain queued behind native render workers waiting for GPU upload completion. Candidate 6's earlier world-close render service resolves that dependency in the matched control above. Network admission and render completion remain separately selectable; broader lifecycle and combined qualification are still required before changing their engineering defaults.

## Executor retirement

`distant_horizons.executor_lifecycle` is an independently configurable, engineering-default-off adaptation for exact DH 3.3.3 on either physical side. The native task picker and its six executors are shared facilities, not individual world identities. Native world unloading shuts those executors down, but their thread-count listeners remain registered. An actual dedicated-server stop then runs a native preset update that recreates all six inner pools through those listeners, after the native shutdown has returned.

The adapter serializes submission, native configuration callbacks, and the transition into shutdown for each executor. Retirement is permanent for that executor. It detaches only that executor's native configuration listener and ignores a callback captured before retirement. The native pool shutdown, running work, termination wait, priorities, and returned pending-task list remain with DH. Listener removal happens after releasing the executor monitor because native configuration dispatch takes the listener-list monitor first. After the native parent's immediate shutdown has returned, the same adaptation cancels only that picker's pending retry and clears its abandoned private queues under the native picker lock. Dispatch checks retirement while holding that lock, including callers already waiting at close. Native termination waits run without the picker lock. The process-wide scheduler remains active, running work retains native completion, and no shared future is cancelled.

Matched native OFF/ON dedicated controls preserve the same decoded 256-column image and normal process exit. OFF recreates the six pools after shutdown and retains six subscriptions; ON leaves all six terminated, with zero running tasks, pending queue entries, or subscriptions. Additional actual-native controls preserve an active pool reconfiguration and a running task's result while shutdown and configuration dispatch overlap. A late direct callback leaves the closed pool unchanged, and post-retirement submission is rejected. These observations establish this subscription/retirement boundary, not collection of all old worlds, client reconnect or a heap/performance improvement.

A separate actual-native paused-picker control retains one private task and keeps scheduling retries after immediate shutdown in the predecessor. With picker retirement enabled, the task is released without execution, no post-close paused checks occur, and the own retry is retired. A separate paused picker still completes its result using the same process-wide scheduler. The interrupted-close control retains the original native interruption cause and lets already-running work finish. These controlled queue states supplement the real-world stop; they are not distant-generation or performance measurements.

The prior executor-subscription repair also passes two actual shader-off full-pack client world epochs with busy disconnect, saved-world reopening, and resource reload. That client result predates the picker-queue retirement extension. The observer identifies two actual shared picker generations, rather than using the current world number as ownership. The first picker/executor weak references naturally clear; the final six executors remain terminated with zero subscriptions, running tasks, queued tasks, or pending retry. All 3,688 observed CPU loans return and 309 observed uploaded VBO generations are deleted in their native context. There are no late enrolled native entries in this case, so the weak old-level admission change does not yet have a positive late-work witness. No collection is forced, and final world collection is not established.

The picker-retirement extension's full-pack counterpart initially stopped at a Traveler's Backpack native key-event configuration read during disconnect, followed by a Create null-game-mode error in incomplete cleanup. That negative is retained without assigning its cause to DH. The fixture now queues its actual native disconnect after its observation tick callback returns and asserts that caller separation. On unchanged product bytes, the next full-pack two-epoch/reload journey exits normally: the final six executors retire, all 3,800 observed CPU loans return, and all 282 uploaded VBO generations receive native deletion. Keyboard handlers remain enabled. This pass does not qualify or repair the separate unloaded-configuration key path, and it establishes no cost or sustained-stability improvement.

## Rendering buffer loans

The native render worker borrows vertex buffers before building upload input and closes those checkouts after joining the upload result. A controlled exception after an actual nonempty upload completed skipped two vertex-checkout returns. The observer saw no active native worker frames or pending uploads, and all observed VBOs were deleted, but the two loans remained unreturned. This is evidence of the native exception edge, not a measured physical-memory leak. A separate normal run returned all 9,452 observed vertex/index loans across busy disconnect, reopen and reload.

Engineering candidate 2 passes the matched post-upload exception control: all 10,468 observed loans return, both world epochs retire, reload produces useful uploads and the native client exits normally. Explicitly disabling the repair on that same product reproduces the two missing vertex returns. A separate exception inside a real native vertex-upload child task leaves two vertex and two index loans unreturned with the repair disabled. With it enabled, DH's own child-future barrier and container cleanup settle the failure, all 6,240 observed loans return, the failed upload's observed VBO is deleted, and reopening and reload complete. These are bounded functional controls, not a physical-memory or performance comparison.

A later no-fault control reaches reopening and then aborts with SIGBUS in the JVM's C2 compiler, while compiling Minecraft's compound-tag loader. Its first epoch returned all observed loans. The fatal report remains an unresolved negative; the native stack does not establish causation or exonerate the adaptation. Do not treat the passing fault controls as complete stability acceptance.

One matched fresh no-fault control instead aborts in native Metal command-buffer completion during initial rendering. This also occurs with Sodium present, so Sodium is not a general workaround for the retained native failures. Stop repeating this normal journey until a backend-specific observation changes the investigation; preserve both fatal reports and the passing fault controls separately.

Two distinct controls on the same frozen product and probe complete normally: all three new DH adaptations disabled, then only the buffer-return adaptation enabled. The latter returns all 7,072 observed loans across disconnect, reopening and reload. These controls qualify the isolated functional path; they do not establish the cause of the combined-path crashes or replace current full-pack acceptance.

The current full-pack shader-off cohort also passes both the all-disabled and all-enabled functional journeys. Each preserves the loaded physical column's four solid cells through saved-world reopening and resource reload. Their two encoded solid runs match exactly; two enclosed material differences per epoch pass the independent native `VISUALLY_EQUAL` admission above. The API's third point is AIR, not another solid run. The enabled path observes 502 native task-service calls inside shutdown, all 3,340 observed CPU loans returned and all 210 observed uploaded VBO generations deleted; both JVMs exit normally. The inputs, experimental-world confirmation and delivered-client-chunk admission are bound to their own fixtures. Work counts differ, so this pair establishes no numerical latency improvement or sustained stability claim, and it does not clear the earlier minimal-client fatal reports.

`distant_horizons.render_resources` is a separate, default-off client adaptation for exact DH 3.3.3. It scopes the native worker's vertex/index checkouts and retains native upload futures, pool operations and error handling. Cleanup returns missing loans only before submission or after the private native upload result establishes completed usage. Pending work retains its bytes; cancellation or unknown partial submission alone cannot authorize recycling. The wrapper does not cancel shared futures, pump tasks or change the original wait.

Native index-return callbacks retain their original loan generation. If worker cleanup already returned that object and another worker reused it, the old callback cannot return the new loan. Identity comparison and a return-once gate preserve normal returns and concurrent cleanup; a failed pool publication is not blindly retried. The helper's unit controls and actual transformed native methods pass. Its bounded native fault, opt-out and isolated normal controls pass at the scope above; complete affected-cohort and lifecycle acceptance remains required before a default change.
