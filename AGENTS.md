## Configuration and interface design

Follow the [configuration binding contract](docs/development/configuration.md). Organize settings by concern → mod → purpose, using recognizable mod names and stable routes. re:form owns shared controls, navigation, focus, draft review, and conflict handling; Compat owns adaptation semantics, validation, permissions, and application timing. Reuse one binding, retained draft, and save path per document across aliases and auxiliary views. Keep standalone defaults useful; author modpack-specific tuning with the pack's configuration owner.

Distinguish local preferences, next-server defaults, running server policy, and observed runtime state. Show loaded, edited, saved, and effective values with their actual timing, including restart or fresh-world requirements. Omission, explicit false, unavailable dependencies, and inactive settings have different meanings. Explain why a setting is inactive and retain its value. Editing an owned document for a future launch must not activate an adapter; foreign editors require the actual admitted native owner. Never infer runtime application from a successful save.

Match controls to the complete accepted domain: types, precision, inclusive or exclusive endpoints, units, and sentinel meanings. Preserve valid exact input and tiny positive values; do not substitute an arbitrary minimum for an open endpoint. Declare probability scales and nominal tick conversions explicitly. Keep coupled validation authoritative and attribute failures to the primary and related fields through structured issues. Registry suggestions must use the correct context and distinguish unavailable, unknown, and resolved-empty results without invalidating supported optional IDs. Presentation labels and captions must not change serialized identities or runtime values.

Use familiar words, sentence case, and consistent action names across controls, help, commands, and diagnostics. Keep editing, validating, saving, applying, reloading, and verifying distinct. Describe an action's actual scope and outcome; reset and default actions must name what they restore. For failures, identify the affected action or value, explain the useful cause or consequence, and offer an available safe next step. Preserve partial results and uncertainty; if a write may have succeeded, direct the user to inspect its state before retrying. Avoid internal implementation terms in routine feedback when ordinary language is sufficient.

Keep actionable feedback near its control and retain errors after transient notifications disappear. Preserve drafts and keyboard focus; support keyboard operation, narration, text scaling, and narrow layouts. Communicate state in text alongside color or icons. Keep translation keys stable when their meaning is unchanged, and preserve fallback meaning and arguments. Derive human and machine reports from the same structured facts; keep diagnostic codes stable and progress separate from JSON output. Retain terminal results independently of progress notifications. A cancellation request does not establish rollback or completed shutdown.

Treat the cost of a valid setting as an implementation concern. Measure the actual native path at representative defaults, accepted extremes, and relevant combinations before restricting the domain. Optimize queries while preserving placement decisions, generation identity, bounded retention, and chunk-loading rules. Explain measured tradeoffs and explicit budget refusals; do not silently clamp valid input or present a cheaper approximation as equivalent. Verify changed controls through their real owner and consumer, including inactive, unavailable, conflict, and failed-application cases as relevant. Source inventories and unit tests do not establish native layout, accessibility, or runtime effects.
